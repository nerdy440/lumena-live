# 11 — Monetization Model

---

## 1. Economy overview

Two currencies, two audiences, one ledger.

| Currency | Who holds it | How acquired | Redeemable? |
|---|---|---|---|
| **Coins** | Viewers | Purchase only (store IAP) | No — non-redeemable by design |
| **Diamonds** | Creators | Received from gifts + private video | Yes — via payout |

Viewers spend coins. Creators earn diamonds. The exchange between them happens only through gifts and private video sessions, and only at the server's declared rates. A creator cannot receive coins directly. A viewer cannot acquire diamonds. There is no coin↔diamond swap, no P2P transfer, and no grey market — these constraints are enforced by the ledger's account `kind` field, which the system checks before any transaction posts.

The split is the standard industry model: this separation is the only architecture that makes chargeback handling tractable. A viewer chargebacks their coin purchase — the coins debit out; the creator's diamonds are not reversed (they are a separate, already-earned asset). The platform absorbs the reversal from its revenue account. Creator earnings are therefore protected from viewer chargebacks. This is a significant competitive differentiator from platforms where a successful chargeback can claw back a creator's already-paid-out earnings.

## 2. Ledger accounts

Every economic actor has one or more ledger accounts. Platform accounts have no `owner_id`.

| Account kind | Currency | Owner | Purpose |
|---|---|---|---|
| `user_coins` | COIN | Viewer | Spendable balance |
| `creator_diamonds` | DIAMOND | Creator | Earnable balance |
| `platform_revenue` | COIN | Platform | Platform's take from gifts |
| `platform_liability` | COIN | Platform | Equals outstanding viewer coin balances (regulatory) |
| `payment_clearing` | COIN | Platform | Coins issued vs. IAP proceeds tracking |
| `promo_issuance` | COIN | Platform | Promotional coins, tracked separately |

Why `platform_liability`? In some jurisdictions, outstanding virtual currency balances are treated as a float and may require reserve. Tracking it as a ledger account rather than a computed value means the compliance report is a `SELECT SUM(balance)`, not a join across millions of rows.

## 3. Gift transaction — full ledger entry set

Viewer A sends a 500-coin gift to Creator B. Platform take is 30%.

```
TRANSACTION: kind=gift, idempotency_key=<uuid>
ENTRIES (must sum to zero):

  viewer's user_coins account:        -500  COIN  (debit)
  creator's creator_diamonds account: +350  DIAMOND (credit, at declared exchange rate)
  platform_revenue account:           +150  COIN  (credit, 30% take)

  (COIN and DIAMOND are different currencies; each currency sums to zero independently)
  COIN sum:    -500 + 150 = -350  ← platform_liability decreases by same amount
  DIAMOND sum: +350               ← platform owes creator 350 diamonds worth of cash

  Additional entries:
  platform_liability:  -350  COIN  (liability decreases as coins are converted to diamonds)
  payment_clearing:    +350  COIN  (tracking that we now owe cash for these diamonds)
```

The double-entry ensures every coin is accounted for. The sum per currency across all accounts in the system is always zero. Nightly reconciliation asserts this and alerts if not.

**Exchange rate** (COIN→DIAMOND): declared in config, not hardcoded. Diamond cash-out rate is declared separately. The spread between them is a second revenue stream on top of the 30% gift take. **Neither rate is exposed in the API or app in a way that makes the spread visible** — the app shows "this gift costs 500 coins" and separately "your diamonds are worth $X." The relationship between those two numbers is not surfaced. This is standard in the category and is disclosed in the terms of service.

## 4. Gift send — client-side contract

The client **never** optimistically updates the balance. The flow is:

```
1. User taps "Send gift"
2. Client shows: confirmation dialog with exact coin cost and new balance
3. User confirms
4. Client sends POST /gifts/send with Idempotency-Key
5. Client shows: loading state (gift button disabled, spinner)
6. Server responds 200: gift_transaction, new_balance
7. Client renders: gift animation, updates balance from server response
8. GIFT_SENT WebSocket event arrives in room for all viewers

OR:
6b. Server responds 402 INSUFFICIENT_BALANCE {shortfall: 200}
7b. Client shows: "You need 200 more coins" + top-up sheet pre-filled with exact shortfall
    Balance is unchanged. No animation. No false success.
```

Step 4 requires an idempotency key. The key is generated by the client before step 3 and stored locally. If the network fails between 4 and 6, the client retries step 4 with the same key. The server returns the original result. The gift is sent exactly once.

## 5. Purchase (order) flow — the C6/C7 fix in detail

```
State machine: CREATED → PENDING_PAYMENT → PAID → CREDITING → CREDITED
               (terminal: FAILED, REFUNDED)
```

```
1. User selects SKU
2. Client sends POST /orders {sku} with Idempotency-Key
   → server creates order in CREATED state, returns order_id
3. Client initiates native store billing (Google Play Billing / StoreKit)
   → store is authoritative; client is a pass-through
4. Store returns purchase token to client
5. Client sends POST /orders/{id}/verify {purchase_token}
   → server verifies token with the store API
   → server checks token_hash uniqueness (replay prevention)
   → on valid: LEDGER transaction (coins credited atomically)
   → order status → CREDITED
   → BALANCE_CHANGED WebSocket event to client
   → response: {status:"credited", coins_credited:10000, new_balance:...}
```

**If step 5 times out or the client crashes:**
- The order remains in `PAID` state (store confirmed; server hasn't credited yet).
- The reconciler (a background worker polling the partial-index on `orders`) picks it up within 60 seconds.
- Reconciler verifies the token with the store, credits if valid, marks CREDITED.
- Meanwhile, `GET /wallet` returns a `pending_orders` list. The UI surfaces: *"Payment received — crediting your account (Order #ORD-8F2K)"* with a live-updating status.
- The user sees what is happening. They see an order ID. They can reference it in support. **Silence never happens.**

**If the token is invalid or already consumed:** order → FAILED. Response includes a support path with the order ID pre-filled.

**No off-platform payment rails.** Not PhonePe QR. Not bank transfer. Not Paytm. Not any method where we cannot independently verify the outcome with the payment provider. This structurally prevents the "paid via QR and got nothing" complaint pattern observed on the reference product.

## 6. Private video billing

Pre-authorization: before the session starts, a hold is placed on the caller's coin balance for the maximum session duration at the declared rate. The hold is a reserved but not yet spent amount.

```sql
-- Hold creation (in the session-start transaction)
INSERT INTO ledger_holds (account_id, amount, expires_at)
VALUES ($caller_ledger_account, $max_coins, now() + interval '2 hours');
```

While the session is active, `PV_BILLING_TICK` events (every 60s) give the client the live meter. These are informational; they do not post ledger entries.

Settlement runs at session end:
```sql
-- Settlement transaction (serializable)
actual_consumed := SUM(ended_at - started_at) from pv_active_intervals (in minutes, ceiling) * rate;
unused := hold.amount - actual_consumed;

-- Post entries
INSERT INTO ledger_entries (transaction_id, account_id, amount) VALUES
  ($tx_id, $caller_coins_account, -actual_consumed),        -- caller debit
  ($tx_id, $creator_diamonds_account, +actual_consumed * (1 - platform_take)),  -- creator credit
  ($tx_id, $platform_revenue_account, +actual_consumed * platform_take);         -- platform

-- Release hold
UPDATE ledger_holds SET consumed=$actual_consumed, state='settled';
-- (unused amount is implicitly freed — it was never debited)
```

If the session ends due to balance exhaustion: settlement is triggered by the hold monitor when `consumed` reaches `amount`. The session terminates gracefully with a 30-second warning at 60s remaining.

## 7. Creator payouts

Payout is gated on:
1. KYC complete (identity + bank/payment account verified)
2. Minimum threshold reached (e.g., 10,000 diamonds)
3. Minimum hold period elapsed since the diamonds were earned (14 days default — the chargeback window)
4. No active account restriction

Payout transaction:
```
creator_diamonds account:  -N  DIAMOND (debit)
platform payout queue:     +N  DIAMOND (debit from liability)
→ triggers bank transfer via payment provider
→ on transfer confirmed: mark payout COMPLETED
→ on transfer failed: reverse diamonds back to creator, FAILED status with reason
```

Payouts never clear instantly. The status machine is: `REQUESTED → PROCESSING → COMPLETED | FAILED`. The creator sees live status. Failed payouts explain why and offer a support path.

## 8. Player protection

Because this product has a real-money economy targeting an entertainment audience, player protection is not optional:

- **Self-set spend limits:** users can set daily / weekly / monthly coin purchase caps. Once set, lowering them is immediate; raising them requires a 48-hour cooling-off period.
- **Cooling-off period:** can be activated by the user at any time; during cooling-off, coin purchases are blocked.
- **Spend visibility:** the wallet's full transaction history with spending totals by period is always accessible. No hiding of total spend.
- **No "surprise" charges:** every gift shows the coin cost before send. Every purchase shows the fiat price before billing.
- **No timed pressure for large gifts:** gifts above a configurable threshold (e.g., 5,000 coins / ≈ $50) display a 5-second countdown confirmation rather than a single-tap send. The countdown is unskippable.
- **Age-adjacent protections:** accounts with recent age assurance (just turned 18) are given a lower default spend cap for the first 30 days. This is disclosed.

## 9. Revenue model summary

| Stream | Mechanism | % of revenue (estimate) |
|---|---|---|
| Gift take | 30% of coin value per gift | ~55% |
| PV billing take | 30% of private video session cost | ~25% |
| Coin/diamond spread | Rate difference between purchase and cash-out | ~10% |
| Premium account features | Subscription (Phase 3) | ~5% |
| Creator tools subscription | Creator dashboard advanced features (Phase 3) | ~5% |

No advertising. The observation that ads interrupt the entertainment and discovery experience that the product is selling, and that advertising networks in this content category carry significant brand-safety risk, makes an ad-free model strategically correct as well as user-friendly.

## 10. What is not exposed to clients

- Platform take percentage
- Diamond cash-out rate relative to coin purchase rate (spread)
- Creator earnings per viewer
- Platform revenue totals
- Other users' balances
- Internal ledger account IDs
- `score_reasons` from any risk or matching model
